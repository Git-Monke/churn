# Churn server dashboard

A small TypeScript app that puts the Jellyfin library, the health of Jellyfin,
Sonarr and Radarr, the live VPN leak status of the torrent stack, and
search/requests for new media in one place.

```
server/
  backend/    Fastify API + serves the built frontend
  frontend/   React + Vite SPA
```

The backend is a BFF: it reads Jellyfin, Sonarr and Radarr APIs, keeps no
database, and never exposes upstream URLs or API keys to the browser. The
frontend only calls `/api/*` on the backend. Login sessions are held in process
memory, so restarting the backend signs everyone out.

## Requirements

- Node.js 22 or newer
- The `server` stack running (Jellyfin, Sonarr, Radarr)
- Churn to finish Jellyfin setup and create the API key (see below)
- A Jellyfin user account to sign in with

## Install and run

```bash
cd server
npm install
npm run dev
```

- UI: <http://127.0.0.1:5173>
- API: <http://127.0.0.1:4000>
- Vite proxies `/api` to Fastify during development.

Production build:

```bash
cd server
npm run build
npm start
# open http://127.0.0.1:4000 — Fastify serves the built SPA
```

The app binds to `127.0.0.1` by default and requires a Jellyfin login. For
access from other machines, put it behind a reverse proxy with TLS; set
`CHURN_COOKIE_SECURE=true` (or rely on `auto` with forwarded HTTPS) so the
session cookie is marked `Secure`.

## Configuration

The backend reads `process.env`, then `server/.env`, then defaults. Process
environment wins. `server/.env` is generated by churn and gitignored; churn
preserves unknown keys, so hand-added settings survive a rerun.

| --- | --- | --- |
| `HOST` | `127.0.0.1` | Backend bind address |
| `PORT` | `4000` | Backend port |

| `JELLYFIN_PUBLIC_URL` | `JELLYFIN_URL` | Jellyfin URL the browser uses for video streams (different in Docker/LAN) |
| `JELLYFIN_API_KEY` | — | Written by churn after Jellyfin setup |

### Live torrent progress

The backend reads qBittorrent's stable `[WebUI]` API key from
`torrent/config/qbittorrent/qBittorrent/qBittorrent.conf` (falling back to the
legacy `WebUI\APIKey` entry). Set `QBITTORRENT_API_KEY` to override it, or
`QBITTORRENT_URL` when qBittorrent is not reachable at
`http://127.0.0.1:8080`. The key is used server-side only, against the read-only
`/api/v2/torrents/info` endpoint; it is never sent to the browser. If the key or
qBittorrent is unavailable, Library falls back to Sonarr/Radarr's queue values.

### VPN status

The Services page has **Services** and **VPN** tabs. The VPN tab calls
`GET /api/vpn`, which asks the torrent stack's `vpn-status` agent to run the
same checks as the fail-closed `vpn-check` container. The agent shares
Gluetun's network namespace, so the result describes qBittorrent's live path.
It returns the Mullvad exit IP/location/server, the DNS resolver, the kill
switch result, IPv6 state, the local firewall exception, and whether
qBittorrent, Prowlarr and FlareSolverr answer on their loopback ports.

The agent listens on `127.0.0.1:8098` only. If the torrent stack is not running,
the tab shows an actionable error instead of failing. Start it with:

```bash
cd torrent && docker compose up -d --no-deps --force-recreate vpn-status
```

If Gluetun itself was recreated, recreate the whole torrent stack instead:
`docker compose down && docker compose up -d`.

### Jellyfin setup and API key

After starting the server stack, churn talks to Jellyfin's HTTP API to finish
first-run setup:

1. It prompts for a Jellyfin admin username and password if Jellyfin is not
   configured yet. The password is not saved by churn.
2. It creates the first admin, completes the startup wizard locally with remote
   access disabled, authenticates, and creates an API key named `churn`.
3. It creates or repairs the `Movies` and `Shows` libraries at
   `/data/media/movies` and `/data/media/tv`. Any `/data` library path is
   removed, because qBittorrent downloads under `/data` and Jellyfin would
   otherwise index files that are still downloading.
4. It writes the key to `server/.env` as `JELLYFIN_API_KEY`. The backend reads
   that file on startup; restart it if it is already running.

Reruns are idempotent: a valid existing key is reused. If the key is missing or
invalid, churn authenticates with the admin credentials and creates/reuses the
`churn` key.

For non-interactive provisioning, set `JELLYFIN_ADMIN_USER` and
`JELLYFIN_ADMIN_PASSWORD` in the process environment or `server/.env`. These are
only installer inputs, not backend settings; the password is never written back.

If you configure Jellyfin manually, create a key under Dashboard → API Keys and
put it in `server/.env`, then restart the backend.

## Authentication and sessions

Every page except the login screen is behind a Jellyfin login. Churn validates
the username and password with Jellyfin (`/Users/AuthenticateByName`), stores
the returned user access token in a server-side session, and writes an opaque
`churn_session` cookie. The cookie is `HttpOnly`, `SameSite=Lax`, path-scoped
and set with `Secure` when Churn is served over HTTPS. Passwords and Jellyfin
access tokens never reach the browser for normal API calls.

Sessions live in a TTL Map in the backend process, keyed by a SHA-256 hash of
the cookie value. There is no database and no session file: restarting the
backend signs everyone out. The default idle TTL is 12 hours; the cookie itself
is kept for 7 days and is replaced on the next login. `POST /api/auth/logout`
clears the cookie, destroys the session and makes a best-effort Jellyfin logout
call.

All logged-in Jellyfin users get the full dashboard. That means any valid
Jellyfin account can search, request media, grab releases, and cancel/delete
titles, which changes global Sonarr/Radarr state. Jellyfin still enforces its own library access
because library and show requests use the user's token, but Churn adds no
admin-only gate of its own. Use separate Jellyfin accounts with non-admin
permissions if you want to limit library visibility.

Auth responses are `no-store`. Failed logins are throttled to 10 attempts per
15 minutes per IP and username. Cross-origin state-changing requests are
rejected in addition to `SameSite=Lax`. Playback uses the signed-in user's
session token, so resume positions and watched state are per Jellyfin user; no
static playback token is stored in `.env`.

## API

| Route | Purpose |
| --- | --- |
| `GET /api/health` | Backend liveness (no session required) |
| `POST /api/auth/login` | Validate Jellyfin credentials and set the session cookie |
| `POST /api/auth/logout` | Destroy the session and clear the cookie |
| `GET /api/auth/session` | Current session state (200 even when signed out) |
| `GET /api/status` | Jellyfin/Sonarr/Radarr health, version and latency |
| `GET /api/vpn` | On-demand VPN leak test from inside the torrent stack's network namespace |
| `GET /api/library` | Jellyfin movies and series with backend-owned poster URLs and provider ids |
| `GET /api/library/images/:itemId` | Poster proxy; no Jellyfin key reaches the browser |
| `GET /api/library/requested` | Sonarr/Radarr library titles, including requested items not yet downloaded |
| `DELETE /api/library/requested/:service/:id` | Cancel the title's queue items, delete it (and its files) from the arr, and refresh Jellyfin |
| `GET /api/library/shows/:source/:id` | Jellyfin/Sonarr show detail with seasons, episodes and download overlays |
| `GET /api/library/shows/:source/:id/releases?season=N` | Sonarr season release search, including rejected and multi-season packs |
| `POST /api/library/shows/:source/:id/releases/grab` | Grab a selected release, overriding automatic restrictions when Sonarr can map it |
| `GET /api/playback/items/:itemId` | Playable item metadata, resume position, media source and same-origin stream URL |
| `GET /api/playback/items/:itemId/stream` | Redirect the media element to Jellyfin's direct stream URL for this session |
| `GET /api/playback/items/:itemId/hls.m3u8` | Redirect to a Jellyfin HLS transcode (H.264/AAC) when the source is not browser-compatible |
| `POST /api/playback/items/:itemId/start` | Report playback start to Jellyfin |
| `POST /api/playback/items/:itemId/progress` | Report playback position and paused state to Jellyfin |
| `POST /api/playback/items/:itemId/stop` | Report playback stop so Jellyfin keeps the resume position / watched state |
| `GET /api/activity` | Active Sonarr/Radarr queue grouped by movie/show |
| `GET /api/search?q=<term>` | Sonarr/Radarr lookup with library-state markers |
| `GET /api/search/images/:service` | Proxied arr media cover |
| `GET /api/requests/options` | Quality profiles, root folders and request defaults |
| `POST /api/requests` | Add a movie or series and optionally start a search |
| `GET /api/services/:id/open` | Redirect to a service's native UI |

Errors use `{ "error": { "code": "...", "message": "..." } }`. Protected API
routes return `401 unauthenticated` without a session and `401 session_expired`
when Jellyfin rejects the stored user token.

## Search and requests

The Search section queries Sonarr and Radarr together with a debounced search.
Results already present in either app are marked **Available** when the arr has
the movie file or every series episode, otherwise **Requested**. Neither can be
added twice. Posters are proxied through the backend, so the browser never sees
an arr URL or API key.

**Request options** stores your preferred quality profile, root folder, TV
monitoring scope, search-on-add and "Prefer smaller files" settings in
`localStorage`. Prefer smaller files is on by default: auto-picking chooses a
720p-only profile first, then a combined 720p/1080p profile, then 1080p-only,
and avoids 4K/Ultra-HD when anything smaller exists. Turn it off to use the
arr's own default (`HD - 720p/1080p`, then `HD-1080p`, then `HD-720p`). The
first accessible root folder, all seasons and search on add are the other
defaults. The Request button uses those settings directly. The backend
re-fetches metadata from the arr by id, validates the selected profile and
folder against the live API, checks for duplicates, then adds the title. Sonarr
gets the chosen monitoring scope; Radarr adds with a `released` minimum
availability.

**Seeders-aware pick** is also on by default. After adding a title, churn asks
the arr for its release list, picks the release with the best seeder count at
the preferred quality tier, and climbs one tier (720p to 1080p, never straight
to 4K) when that tier has no torrents above **Minimum seeders** (default 5). A
tier climb the quality profile would reject is grabbed with an explicit
override; releases rejected for anything other than quality are never
auto-overridden. Usenet releases always count as healthy. Movie requests grab
the pick directly; show requests grab well-seeded single-season packs and let
Sonarr's `SeasonSearch` handle seasons without one. If the search or grab
fails, churn falls back to the arr's own `MoviesSearch`, `SeasonSearch` or
`SeriesSearch` command. The show release list marks the same pick as
**Recommended** with the reason. Turn the switch off to keep the arr's original
search-on-add behaviour.

Indexer seeder counts can be tracker inflation, so churn also checks the real
swarm. About a minute after a smart grab it reads qBittorrent's connected seeds
(`num_seeds`) and speed. When fewer than **Minimum seeders** are connected and
the speed is below 300 KB/s before 25% completion, it removes and blocklists
the stalled queue item, then grabs the best-seeded alternative from the same
search result set. The alternative must be at least 1.5× the stalled release's
reported seeders, must not be a lower quality tier, and must stay within one
tier of the profile. Only one re-pick is attempted per request. If the
replacement grab fails, the arr's normal search command runs again. Re-picks
appear as a dismissible notice on the Library page and in `/api/activity` as
`repicks`.

Search stays usable when one app is down: the other app's results are still
returned and an alert explains the unavailable service.

## Library and activity

The dashboard is split into Services, Library and Search pages using lightweight
hash routes (`#/services`, `#/library`, `#/search`). Services has **Services**
and **VPN** tabs; the VPN tab runs its test when opened and on demand.

`/api/activity` reads the Sonarr and Radarr v3 queues in parallel and returns
only active records: queued, downloading, importing, or waiting on import.
Failed and already imported records are excluded. Queue records are grouped by
movie or show, with aggregated progress, ETA, size, download client, protocol,
quality and warnings. Arr metadata supplies display titles and posters, proxied
through the same backend image routes as search.

The Library page merges `/api/library`, `/api/library/requested` and `/api/activity`:

- duplicates are matched by Radarr `tmdbId` or Sonarr `tvdbId` and shown once;
- unmatched active downloads appear as their own cards;
- Sonarr/Radarr titles that have downloaded but not reached Jellyfin appear as
  **Scanning** cards;
- if Jellyfin still has not indexed a completed title after 2 minutes, the card
  shows **Scan problem** until the item appears;
- tracked titles with no downloaded file yet appear as **Requested** cards;
- active downloads sort before available titles;
- a broken arr only shows an alert for that service and does not hide Jellyfin
  or the other arr.

Cards backed by Sonarr or Radarr have a trash button. It opens a confirmation
dialog, then `DELETE /api/library/requested/:service/:id` removes every queue
record for that title with `removeFromClient=true`, deletes the movie or series
with `deleteFiles=true`, and asks Jellyfin to refresh its library. This stops an
in-progress download and clears the Radarr/Sonarr entry so the title can be
requested again with a smaller quality profile. Deleting a completed title also
deletes its media files.

The backend also watches qBittorrent every second. When a torrent transitions to
complete, or is first seen as recently completed (within 10 minutes), it asks
Jellyfin to refresh its library. This runs even when no dashboard tab is open.
While a Library card is **Scanning**, the page polls Jellyfin every 2 seconds so
the card becomes playable as soon as the item is indexed. There is no separate
manual scan endpoint; if Jellyfin indexes later, the card still recovers from
the **Scan problem** state automatically.

Movies stay at card level. Clicking a show opens
`/api/library/shows/:source/:id`, which unions Jellyfin and Sonarr episodes by
season/episode. Per-episode downloads and Sonarr season packs are overlaid on
the episode list, and Jellyfin shows are matched to Sonarr through Jellyfin
`ProviderIds.Tvdb`.

Multi-season packs such as `S01-03` are recognised from the release title, so
their download progress appears on every covered season even when Sonarr only
reports one season in its queue. Shared queue records are counted once when
totalling download size.

For Sonarr-backed shows, **Choose release** runs a season search and lists every
release Sonarr returned, including rejected releases and multi-season packs. The
**All seasons** action searches the show's other seasons and merges any
multi-season packs that cover the selected season, which catches packs Sonarr
files under their first season (for example `S01-05`). The list shows size,
quality, indexer, seeders, season coverage and rejection reasons; the smallest
mapped multi-season pack is marked recommended when no release is automatically
eligible.

Missing individual episodes also get their own **Choose release** action. That
uses Sonarr's episode-id search instead of its season search, so single-episode
releases are available even when no season pack exists. After requesting a
series, churn opens the picker immediately for the first monitored season so you
can choose a release while Sonarr's automatic search runs in the background. If
no releases are found, the picker stays open with retry and all-seasons actions.
Grabbing a rejected release overrides Sonarr's decision engine using the episode
ids Sonarr mapped. Upstream GUIDs, magnet URLs and indexer ids stay on the
backend. A show that exists only in Sonarr still opens a Sonarr-backed detail
page.

## Playback

Movies in Library and episodes in show detail open `#/play/<itemId>`, an HTML5
`<video>` page backed by Jellyfin. Playback is per Jellyfin user: the item's
resume position comes from Jellyfin `UserData`, and start/progress/stop reports
keep Jellyfin's Continue Watching and watched state in sync.

Video bytes are not proxied through Churn. Playback is codec-aware:

- Browser-compatible sources use a same-origin
  `/api/playback/items/:itemId/stream` URL. The backend validates the session
  and returns a `302` to Jellyfin's `static=true` stream with the user's access
  token as `api_key`. Seeking works because Jellyfin serves byte ranges.
- Other sources (for example HEVC video with AC3 audio in an MKV) use a
  same-origin `/api/playback/items/:itemId/hls.m3u8` URL. The backend returns a
  `302` to Jellyfin's HLS manifest with explicit H.264/AAC transcode parameters
  based on the source resolution and bitrate. The frontend plays it with
  `hls.js`, with native HLS as a fallback.

The token never appears in the page DOM or API responses, but it is visible in
browser devtools, redirect targets and Jellyfin HLS playlist/segment URLs. That
is the accepted tradeoff for stream redirection; a backend proxy would be needed
if Churn is exposed beyond the LAN.

Set `JELLYFIN_PUBLIC_URL` when the browser reaches Jellyfin at a different
address than the backend (for example a LAN IP instead of a Docker service
name). Playback failures show the media error alert with an **Open Jellyfin**
fallback.

## Container later

The app is environment-driven so it can be containerised later:

- `HOST=0.0.0.0` and join the server Compose network;
- use service DNS names, e.g. `JELLYFIN_URL=http://jellyfin:8096`;
- pass API keys via environment;
- if relying on `config.xml` discovery, mount
  `server/config/{sonarr,radarr}` read-only.
