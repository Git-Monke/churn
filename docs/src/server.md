# Server stack

The server stack is the media-facing half of the setup. It runs outside the
VPN because it serves the local library and provides the automation APIs used
by the torrent stack.

## Services

| Service | Role | Host port |
| --- | --- | --- |
| `jellyfin` | Media server and player frontend | `8096` |
| `sonarr` | TV series management and downloads | `8989` |
| `radarr` | Movie management and downloads | `7878` |
| `server-init` | One-shot setup for media folders and root folders | none |

## Storage

Every service mounts the same host directory as `${DATA_DIR}` at `/data`.
Jellyfin reads the media library from `/data/media`, and Sonarr/Radarr use the
same paths for their libraries and completed downloads. Keeping one path layout
avoids translation between the two stacks.

`server-init` creates:

```text
/data/media/tv
/data/media/movies
```

It also sets ownership to `PUID`/`PGID` and registers those directories as the
Sonarr and Radarr root folders. The one-shot is idempotent and can be rerun:

```bash
cd server
docker compose run --rm server-init
```

Do **not** add `/data` itself as a Jellyfin library root. qBittorrent saves
downloads under `/data` and incomplete files under `/data/incomplete`, so a
root-level library makes Jellyfin index media that is still downloading.
Churn creates or repairs the `Movies` and `Shows` libraries at
`/data/media/movies` and `/data/media/tv`, removes any `/data` library path it
finds, and is safe to rerun.

## Configuration

`server/.env` is generated by churn and holds `DATA_DIR`, `PUID`, `PGID`, and
`TZ`. The compose file is static. Web UIs are published directly by each
service, so they are reachable at:

- Jellyfin: `http://<host>:8096`
- Sonarr: `http://<host>:8989`
- Radarr: `http://<host>:7878`

The torrent stack's `prowlarr-init` reads the Sonarr and Radarr API keys from
`server/config/`. This is why the current wiring expects both stacks on the
same machine.

## Dashboard

The optional TypeScript app in `server/backend` and `server/frontend` serves a
single dashboard for the Jellyfin library, the health of Jellyfin, Sonarr and
Radarr, and searching and requesting new media. Requests are added through the
Sonarr/Radarr APIs so the existing Prowlarr and qBittorrent pipeline starts the
download. The app binds to `127.0.0.1` and the browser only calls the backend;
upstream keys and URLs stay server-side.

```bash
cd server
npm install
npm run dev        # UI http://127.0.0.1:5173, API http://127.0.0.1:4000
```

After the server stack starts, churn completes Jellyfin's first-run wizard,
creates an API key named `churn`, and writes it to `server/.env` as
`JELLYFIN_API_KEY`. It asks for the Jellyfin admin username and password when
needed; the password is not stored. Sonarr and Radarr API keys are read from
`server/config/*/config.xml` unless overridden.

The dashboard requires a Jellyfin login. Churn stores the returned user token in
an in-memory session and sends only an HttpOnly session cookie to the browser;
restarting the backend signs everyone out. Library calls use the user's token,
while the installer's API key stays server-side for status checks. All
logged-in Jellyfin users get the full dashboard, including Sonarr/Radarr
requests.

The planned order is: library/status dashboard, search and media requests
(done), active downloads in Library (done), Jellyfin login and per-user sessions
(done), download history and queue actions, then Jellyfin playback controls. See
[Web dashboard](web-ui.md) for the current API and configuration.
